# Phase 2 — UI Design Contract (Process Management & Smart Kill)

> Visual and interaction contract for process detail inspection, smart kill escalation, and whitelist-gated protection. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>

## Layout & Spacing

Terminal character-cell grid. All new surfaces are overlays — the port table is never squeezed (D-05).

### Overlay Geometry (Phase 2 additions)

| Surface | Position | Size | Background | Rows Left Visible (80x24) |
|---------|----------|------|-----------|---------------------------|
| Detail panel | Top-anchored in content area (`y = content_area.y`) | Full content width × **12 rows** | `bg.overlay` | 9 table rows below |
| Confirm dialog | Centered popup (`x = (w-60)/2`, `y = content_area.y + (h-7)/2`) | **60 cols × 7 rows** | `bg.overlay` + bordered `Block` | Table dimmed behind — dialog is the topmost layer |
| Whitelist overlay | Top-anchored in content area | Full content width × **content height − 1 rows** (20 at 80x24) | `bg.overlay` | 1 row below (overlay claims the surface; table interaction under it is not meaningful) |

### Overlay Stack (render order — later renders on top)

```
table → search (3 rows, pushes table down, Phase 1) → filter (7 rows, pushes table down, Phase 1)
      → detail panel (12 rows, Clear-over) → whitelist overlay (Clear-over) → confirm dialog (centered popup, topmost)
```

Coexistence rules:
- Search + filter: unchanged Phase 1 stacking (search above filter; both push the table down).
- Detail + search/filter: render in stack order; a later overlay covers an earlier one. No special handling — closing the top overlay reveals the one below.
- Whitelist + anything: whitelist renders above all but confirm.
- Confirm dialog: always topmost; while open, `x` is intercepted (no double-kill fire).

### Detail Panel Internal Layout (12 rows)

```
Row 0:  ┌─ {name} — PID {pid} ─── [{protection badge}] ─ [Esc] ─┐
Row 1:  │ Status: Running | Exited                              │
Row 2:  │ Owning port: 8080 (TCP)                               │
Row 3:  │ Executable path: …\nodejs\node.exe                    │
Row 4:  │ Command line: node server.js --port 8080 …            │
Row 5:  │ Start time: 09:41:12 31-Jul-2026                      │
Row 6:  │ Parent PID: 7812                                      │
Row 7:  │ Signature: Signed | Unsigned | Unknown | Verifying…   │
Row 8:  │ Protection: System-critical | On your list | None      │
Row 9:  │ Reason: {plain-language reason, only when protected}   │
Row 10: │ Hint: Press x to terminate | …confirmation required    │
Row 11: └───────────────────────────────────────────────────────┘
```

Label column: fixed 17 chars (`"Executable path:"` = 16 + space), value column takes the rest. Values truncate (see UI Considerations §overflow).

### Whitelist Overlay Internal Layout (20 rows at 80x24)

```
Row 0:  ┌─ Protection Whitelist ─────────────────── [Esc] ─────┐
Row 1:  │ Built-in — system-critical, cannot be terminated      │
Rows 2-10: built-in list (9 rows, scrollable; ◆ name + short reason)
Row 11: │ User list — termination requires confirmation         │
Rows 12-16: user list (5 rows min, scrollable; → full path)     │
Row 17: │ Path: >_  {add input, search-bar input pattern}       │
Row 18: │ [j/k]Move [d]Delete [Tab]Focus [Enter]Add [Esc]Close  │
Row 19: └───────────────────────────────────────────────────────┘
```

Constraints: Title `Length(1)`; built-in label `Length(1)`; built-in list `Length(9)` (scrollable, `j`/`k`); user label `Length(1)`; user list `Min(5)` (scrollable); input `Length(1)`; hint `Length(1)`. Scrollbar per Phase 1 pattern (`│` track, `█` thumb) on both lists when content overflows.

### Defaults Note

Overlay sizes above are defaults (researcher-selected): D-05 mandates no table squeeze (⇒ Clear-over, not push-down); the 12-row detail panel keeps ≥9 table rows visible at 80x24 while fitting all 9 fields; the 20-row whitelist overlay gives both lists + input room to edit at minimum terminal size.

## Color

Phase 1's 12-slot One Dark theme is unchanged (verified against `port-tui/src/theme.rs` — all slots present, `accent_secondary` currently unused). **Delta: `accent.secondary` is now assigned; protection states get a marker.**

### Accent Split (10%)

| Slot | Value | Reserved For (exhaustive) |
|------|-------|---------------------------|
| `accent.primary` `#61afef` | Phase 1 list unchanged | Active tab, search/filter prompt, focused element border, footer hotkey underlines, selection indicator |
| `accent.secondary` `#c678dd` | **NEW — kill-action highlights only** | `[x]` kill hint in footer, `[y] Confirm kill` button in confirm dialog, `[d] Delete` hint in whitelist overlay, "Press x to terminate" hint text in detail panel |

**`accent.secondary` is never applied to error text (that is `status.error`), never to static content, and never to non-kill interactive hints.**

### Protection Semantics (new)

| State | Marker in Process column | Row style | Where Determined |
|-------|--------------------------|-----------|------------------|
| Built-in whitelist (hard block) | `◆` in `status.error` | Normal (dim only if non-admin, per below) | port-core built-in list (basename match; PID 4/0 special-cased) |
| User whitelist (confirmation gate) | `◆` in `status.warning` | Normal | settings.toml `whitelist` entries (full-path match) |
| Not protected | — | Normal | — |

- `◆` (U+25C6) prefixes the process name in the table. It is shown in both admin and non-admin sessions.
- Cosmetic row dimming (Phase 1 heuristic: PID < 1000 or known name) is **superseded**: dimming is now driven by whitelist membership and shown only when **non-admin** (limited detail, SCAN-07/D-09 precedent). Admin sessions render protected rows at full brightness with the `◆` marker.
- Signature row: `Signed` → `status.success`; `Unsigned` → `status.warning`; `Unknown`/`Verifying…` → `fg.muted`.

### Semantic Reuse (no new slots)

| Event | Color |
|-------|-------|
| Kill success `✓` | `status.success` |
| Kill failure `✗`, hard-block message, kill access denied | `status.error` |
| User-confirm gate notice, confirm badge, unsigned signature | `status.warning` |
| Whitelist add/remove confirmations | `status.info` |

60/30/10 split unchanged: `bg.base` dominant, `bg.surface`/`bg.overlay` secondary, `accent.primary`+`accent.secondary` combined 10%.

## Copywriting Contract

All Phase 1 copy stands. Phase 2 additions (user-facing strings — English; `.zh.md` not required, per 02-CONTEXT specifics: `**/*.zh.md` gitignored):

### Primary CTA

| Element | Copy |
|---------|------|

### Kill Flow Copy

| Step | Copy | Color |
|------|------|-------|
| Graceful attempt started | `Terminating {name} (PID {pid}) — sending graceful close…` | `fg.default` |
| Graceful timeout hit | `Graceful close timed out ({kill_timeout_secs}s) — force killing {name} (PID {pid})…` | `fg.default` |
| Success — graceful | `✓ {name} (PID {pid}) terminated gracefully` | `status.success` |
| Success — force (after timeout) | `✓ {name} (PID {pid}) force-killed` | `status.success` |
| Success — direct (no GUI/console window) | `✓ {name} (PID {pid}) terminated` | `status.success` |
| Failure — access denied (D-03) | `✗ Cannot terminate {name} (PID {pid}) — admin rights needed. Press a to elevate.` | `status.error` |
| Failure — already exited | `✗ {name} (PID {pid}) already exited` | `status.error` |
| Failure — other | `✗ Failed to terminate {name} (PID {pid}): {reason}` | `status.error` |

All kill outcomes appear in the **existing status bar** (D-04) — no toast component. Successful kills immediately trigger one scan so the freed port disappears.

|---------|------|

| Buttons | `[y] Confirm kill` (accent.secondary) · `[n] Cancel` (muted) |

### Hard Block (built-in whitelist, D-09)

No kill path exists for built-in entries — `x` on a hard-blocked process never opens the confirm dialog (D-09 hard block).

### Error States (new)

| Element | Problem Description | Next Step |
|---------|--------------------|-----------|
| Kill access denied | `✗ Cannot terminate … admin rights needed` (red, D-03) | `Press a to elevate.` — no auto-elevate, no state-loss relaunch (D-03) |
| Detail fetch failure | Field values render `—` dim | Panel keeps name/PID from scan data; close and re-open to retry |

### Destructive Actions

| Action | Confirmation Approach |
|--------|----------------------|
| Terminate non-protected process (PROC-03 instant default) | No dialog — kill is instant; outcome in status bar (D-04) |
| Terminate user-whitelisted process (PROC-03, D-09) | Confirmation dialog (60×7 centered popup): `[y] Confirm kill` / `[n] Cancel` — plain-language reason shown |
| Terminate built-in whitelisted process (PROC-04) | **Hard block — no kill path exists.** Explanation shown in status bar + detail panel; `w` hint to review whitelist |
| Remove user whitelist entry | **No confirmation** — instant (D-15 immediate effect); status bar confirms `Removed {path}`. Reversible by re-adding. |

## Keyboard Contract

### Keybinding Layers — Deltas

**L0 Universal — unchanged** (Esc semantics now overlay-aware: detail → close, whitelist → close, confirm → cancel).

**L2 Actions — three new keys registered** (`d`, `x`, `w` — none currently bound; verified `main.rs:281` conflict `k`→MoveUp untouched):

| Key | Action | Notes |
|-----|--------|-------|
| `d` | Toggle detail panel (D-06) | Open on Ports tab; selected row is the data source; open panel refreshes on selection change |
| `x` | Kill owning process (D-01) | Non-protected: instant. User whitelist: opens confirm dialog. Built-in: hard-block message (no dialog) |
| `w` | Toggle whitelist overlay (D-14) | Available from any tab |

**L2-confirm (new mini-layer, confirm dialog open):**

| Key | Action |
|-----|--------|
| `y` / `Enter` | Confirm kill (escalation proceeds) |
| `n` / `Esc` | Cancel — close dialog, process untouched |

**L3 Power — unchanged.**

**Still reserved:** `Space` (selection toggle — Phase 2 has no multi-select; "Kill all"/batch is out of scope, REQUIREMENTS.md) and `Enter` on a table row (detail is via `d`).

### Pass-Through Rules (per overlay — Phase 1 search/filter precedent)

| Overlay | Intercepted keys | Pass-through (table stays live) |
|---------|------------------|---------------------------------|
| Detail panel | `d` (close), `Esc` (close) | `j` `k` `↑` `↓` `r` `s` `g` `G` `/` `f` — selection change refreshes panel (D-06) |
| Confirm dialog | `y` `n` `Enter` `Esc` `x` (x no-op — prevents re-trigger) | All other keys |
| Whitelist overlay | `j` `k` `↑` `↓` (user-list focus), `d` (delete selected entry), `Tab`/`Shift+Tab` (focus user-list ↔ input), printable chars + `Backspace` + `←` `→` (input focus), `Enter` (add path / commit), `Esc` (close) | `r` `s` and L0 tab/quit keys |

**Whitelist overlay exception (declared):** `j`/`k` do NOT pass through to the table when the user list is focused — the overlay covers the table, so invisible table movement would be confusing. This deviates from the strict Phase 1 pass-through pattern and is deliberate. When input is focused, `j`/`k` also stay with the overlay (input owns printable keys per search-bar precedent).

### Focus Management — new states

| State | Visual Indicator | Active Keys |
|-------|-----------------|-------------|
| Detail panel open | Overlay with `bg.overlay`; title Bold `fg.emphasis`; selection still Reverse on table rows below | `j` `k` move selection (panel refreshes), `d`/`Esc` close, `x` kill |
| Confirm dialog open | Centered bordered popup; `[y]` underlined accent.secondary, `[n]` underlined muted | `y`/`Enter` confirm, `n`/`Esc` cancel |
| Whitelist — user list focused | Selected entry Reverse; scrollbar visible when overflowing | `j` `k` move, `d` delete, `Tab` to input |
| Whitelist — input focused | `Path: >_` with block cursor (search-bar pattern) | text input, `←` `→` cursor, `Enter` add, `Tab` to list, `Backspace` |
| Whitelist — built-in section | Read-only list, `◆` prefix, `fg.muted` names, Dim | Not focusable — scrolls with list focus only if needed (declared: built-in section is not independently scrollable; its 9 rows show the top entries, remainder accessible via `j`/`k` when user list is empty — see UI Considerations §overflow) |

### Message Additions (update.rs / message.rs integration)

`Kill {pid}` · `KillConfirmed {pid}` · `KillCancelled` · `KillStart` (status bar) · `KillOutcome {result}` (success/failure enum with reason) · `ToggleDetailPanel` · `DetailDataLoaded {process_info}` · `SignatureVerified {is_signed: Option<bool>}` · `ToggleWhitelistOverlay` · `WhitelistFocusNext` · `WhitelistFocusPrev` · `WhitelistSelectMove {dir}` · `WhitelistDeleteSelected` · `WhitelistInput(char)` / `WhitelistBackspace` / `WhitelistCursorMove {dir}` · `WhitelistAdd {path}` · `WhitelistSaved` · `ProcessExited {pid}` (refresh-time exit detection while panel open). All async results flow through the existing `mpsc` → `update()` → render pipeline (D-10 Phase 1 pattern).
